# 首次加载性能优化设计

## 目标

降低首次访问时字体、照片和应用代码的等待时间，同时保证未来新增的任意中文字符仍能使用完整的“悄悄话手写”字体。优化覆盖公共首页、公共路由、社群路由、静态资源缓存和真实用户性能监测。

## 已批准方案

### 1. 两级手写字体

- 从完整字体生成一个只覆盖首页、导航和页脚当前字符的关键子集。
- CSS 使用两个不同字体族：`Qiaoqiaohua Critical` 在前，版本化完整字体 `Qiaoqiaohua Handwriting Full` 在后。
- 当前字符只请求关键子集；子集缺少的新字符自动回退到完整字体并按需下载，因此未来内容不会失去手写效果。
- 保留 TanukiMagic 和现有汉字修补字体的字符路由。
- 删除 Google Fonts `@import`，最后使用系统中文字体作为网络失败时的即时后备。
- 不预加载 6.24 MB 完整字体；只预加载小型关键子集。

### 2. 首页图片

- 为首页的大图生成 640px 与 1280px WebP 版本，保留原图作为高分辨率候选。
- 使用 `srcset`/`sizes`，让手机不再下载 1920px 或 4K 原图。
- 首屏吉祥物保留高优先级；首屏以下图片全部懒加载。
- 轮播只挂载当前项及相邻项的图片，避免隐藏幻灯片提前占用带宽。
- 保留明确的宽高，防止布局偏移。

### 3. JavaScript 与渲染边界

- 首页保留同步入口，其余公共页面使用 `React.lazy` 路由拆分。
- 整个 Community 路由作为独立懒加载入口；Auth、权限守卫、社区页面和 Community Chrome 不进入公共首页启动路径。
- 保持现有路由 URL、权限逻辑和视觉过渡；懒加载期间显示轻量、稳定尺寸的页面占位。
- 暂不进行框架迁移或 SSR，以较低风险先获得主要收益。

### 4. 缓存

- Vite 生成的 `/assets/*` 哈希资源使用一年 `immutable` 缓存。
- 字体采用版本化文件名并使用一年 `immutable` 缓存。
- 公共图片使用较长缓存和 `stale-while-revalidate`；HTML 保持重新验证。
- 部署后核对 Cloudflare 是否覆盖 Vercel响应头。

### 5. 真实用户性能数据

- 在现有第一方匿名网站分析中增加 LCP、CLS、INP、FCP、TTFB 指标。
- 记录规范化页面路径、指标名称、数值、评级、导航类型和粗粒度网络类型；不记录 URL 查询值、IP、账户、设备指纹或跨会话标识。
- 指标在页面隐藏或生命周期结束时上报，并继续使用现有会话级匿名标识和后端校验。

## 备选方案与取舍

1. **关键子集 + 完整字体按需回退（采用）**：当前首页最快，未来字符效果完整；新增关键首页文字可能触发完整字体，之后可重新生成子集。
2. **常用 2,500 汉字子集 + 完整回退**：未来常见文字更少触发完整字体，但首载子集仍可能达到 MB 级，收益较低。
3. **仅完整字体**：维护最简单且覆盖完整，但保留当前 6.24 MB 首载瓶颈，不满足目标。

## 验收标准

- 首页当前中文只需要关键字体子集，模拟一个子集外字符时会请求完整字体并保持手写效果。
- 首页下面的轮播图片不再 eager；手机候选宽度不超过布局所需。
- 首页主 JavaScript gzip 体积显著低于优化前 615.56 KB，Community/Auth 不在首页初始模块图中。
- 哈希资源与版本化字体返回长期 immutable 缓存头。
- Core Web Vitals 事件通过现有匿名分析边界校验，测试不包含任意查询参数或个人数据。
- 测试、TypeScript、生产构建和冷缓存浏览器检查通过。
