# 社群邮箱认证修复设计

## 目标

修复正式站邮箱注册确认后长期停留在“正在完成登录”以及邮箱密码登录返回 503 的问题，并同时提供以下入口：

- 用户名或邮箱 + 密码登录；
- Magic Link 登录；
- 邮箱验证码登录；
- 注册后的链接或验证码双通道邮箱确认。

## 认证架构

浏览器继续使用 Supabase publishable key。邮箱密码登录直接调用 Supabase Auth，避免依赖仅用于用户名解析的服务端接口；只有不含 `@` 的用户名继续调用 `/api/community/username-login`。服务端用户名登录仍使用 secret key、限速和 `resolve_login_email_server`，正式环境必须补齐对应变量。

Magic Link 和邮箱验证码都由 `signInWithOtp` 发送，并设置 `shouldCreateUser: false`，避免绕过年龄选择和注册流程创建账号。验证码由 `verifyOtp({ email, token, type: 'email' })` 验证。托管 Supabase 的 Magic Link 邮件模板同时包含 `{{ .ConfirmationURL }}` 和 `{{ .Token }}`，让同一封邮件支持两种完成方式。

注册继续收集年龄范围、邮箱和密码，并把 `age_band` 写入用户元数据。Supabase 注册确认邮件也同时呈现确认链接和验证码；提交注册后，页面进入确认步骤，允许直接输入验证码或打开邮件链接。

## 页面与状态

登录页保留“登录 / 注册”主切换。登录区域提供密码、Magic Link、邮箱验证码三个清晰入口；找回密码保持辅助入口。验证码发送成功后在原卡片内进入六位验证码输入状态，保留邮箱展示、返回和重新发送操作。

注册成功但尚无 session 时进入邮箱确认状态，不再只显示静态通知。确认成功后统一前往 `/community/enter`，由既有社群状态路由决定下一页。

认证回调页显式处理 URL 错误、会话建立、超时与无会话状态。成功时进入 `/community/enter`；失败时显示可读提示，并提供返回登录和重新尝试按钮，避免无限加载。

## 错误与安全

- 邮箱密码登录不依赖 secret key；用户名登录的服务端错误会明确提示可改用邮箱或无密码登录。
- Magic Link 和验证码请求不暴露邮箱是否存在。
- 验证码只接受六位数字，并展示过期、错误、限速和网络失败状态。
- 重发按钮带短暂冷却，避免误触和邮件限速。
- 浏览器不接触 `SUPABASE_SECRET_KEY`；正式环境配置只在服务端保存。

## 验证

- 服务层测试覆盖邮箱/用户名密码路由、OTP 发送和 OTP 验证。
- 页面测试覆盖三种登录入口、注册确认步骤、验证码提交和错误提示。
- 回调测试覆盖成功、URL 错误和无会话失败状态。
- 运行相关 Vitest、应用与后端类型检查、lint 和生产构建。
- 检查正式站用户名接口不再返回 503，并验证 Supabase 邮件模板同时含链接和验证码。
