# 社群密码安全流程设计

## 目标

把社群内的注册、密码重置和登录账号设置升级为一致、可信且易理解的密码体验：所有新密码必须再次确认；已登录用户修改密码前，必须通过当前账号邮箱收到的 6 位验证码完成二次验证。

## 选定方案

采用站内分步验证流程：用户在“设置 → 登录账号”发起修改密码，系统向当前邮箱发送一次性验证码；邮件发送成功后，展示验证码、“新密码”和“确认新密码”字段，最终提交时由 Supabase 同时验证验证码并更新密码。此方案沿用已有 Supabase Auth 能力和社群表单语言，不新增自建验证码存储或独立邮件服务。

相较于仅发送密码重置链接，站内验证码流程上下文更连续；相较于自建验证码接口，使用认证服务自带的重新认证机制能减少敏感凭据处理和安全维护面。

## 界面与状态

### 注册

- 账号信息步骤增加“确认密码”。
- 两次输入实时显示是否一致，并在不一致时阻止提交。
- 密码提示明确至少 8 个字符；字段使用正确的 `autocomplete` 属性。

### 已登录修改密码

- 邮箱展示与密码修改拆成独立区块，避免一个“保存账号修改”按钮同时触发两种安全含义不同的操作。
- 初始状态只显示当前邮箱和“发送验证码”。
- 发送后显示 6 位验证码输入、倒计时和重新发送入口。
- 验证码发送成功后才显示“新密码”“确认新密码”和提交按钮；验证码在最终提交时完成服务端验证。
- 修改成功后清空所有敏感输入并回到初始状态，显示明确成功反馈。
- 邮箱修改仍保留原有能力，但使用独立按钮与独立结果提示。

### 密码重置

- 邮件重置链接落地页增加“确认新密码”。
- 两次输入不一致或少于 8 个字符时不调用更新接口。

## 数据流与安全边界

1. 已登录用户调用 Supabase Auth 的重新认证能力，验证码发送到当前账号邮箱。
2. 用户输入验证码后，客户端将验证码作为重新认证 nonce 随密码更新请求提交。
3. Supabase Auth 验证 nonce 并更新密码；应用不持久化验证码或明文密码。
4. 所有敏感输入只保存在当前组件状态，成功后立即清空。
5. 服务端错误映射为不泄露账号状态的用户可读提示。

## 校验与可访问性

- 新密码最少 8 个字符，确认密码必须完全一致。
- 验证码只接受 6 位数字。
- 每个字段有显式标签，错误提示使用 `role="alert"`，成功提示使用 `role="status"`。
- 发送、验证和保存期间按钮进入忙碌状态，防止重复提交。
- 中英文文案同步更新。

## 验证范围

- 为注册、设置页和重置页补充组件测试：确认密码必填、密码不一致被拦截、验证码发送、带 nonce 更新密码、成功清空状态。
- 为认证 service 补充重新认证与带 nonce 更新密码的调用测试。
- 运行聚焦测试、应用类型检查和生产构建。
- 启动本地页面并检查桌面与移动尺寸下的视觉、键盘操作和状态反馈。
